# RyzenHV 0.7.28 (GA403WM): VZ probe (stage 0 of the in-kernel APIC plan)

On top of 0.7.27 (research/exit-reasons ca7da15). This is debugging only: with the probe off (the default), nothing changes for any client.

## Why
A RyzenHV-only LAPIC fast path for HyperKit is impossible: HyperKit keeps IRR, ISR, PPR and the timer in its own user-space vlapic, so
the kernel cannot handle an EOI, TMICT or ICR write without desyncing it. The route left is Docker on Virtualization.framework (VZ) with an
in-kernel APIC in RyzenHV. Stage 0 finds out whether VZ gets past `hv_vm_create(0x400)` here, and what it calls next.

## What it adds
- `rhv-info hv vzprobe [0|1]` (kRHVHvVzProbe = 16; root to change, anyone can read). While it is on:
  - `hv_vm_create` with flag 0x400 (the in-kernel APIC variant) is accepted as a plain VM. The in-kernel APIC is **not** emulated, so the
    guest gets no interrupts and does not boot.
  - Every `vm_create` logs its flags and the client's process name.
  - The stub traps (task 2/3/8-11/14/15, thread 6/8/13-15) answer success and log their first 400 calls at INFO, with argument words.
  - `kern.hv_support` reads 1. The probe takes it unless it was already taken, and gives it back when the probe goes off.
- Off by default, not settable by boot-arg. HyperKit never takes these paths: it never sets 0x400 and never calls a stub trap.
- No new kernel imports (408, the same as 0.7.27). Stats ABI unchanged (V6).

## How to run it
`ga403wm-power/scripts/vz-probe.sh`: one root dialog switches the probe on, follows the RyzenHV log, and switches it off again however
the run ends. Start Docker once with `UseVirtualizationFramework=true` while it waits, then quit Docker and put the setting back.
